| Q | `RESET RESERVANEX` has no environment restriction | **RESUELTA (Fase 10 Paso 3).** `resetQaDataExceptSuperAdminAction` now requires `ALLOW_GLOBAL_TENANT_RESET=true` (checked via `isGlobalTenantResetAllowed()` in `apps/web/src/lib/global-tenant-reset.ts`, exact-string match, fail-closed by default) in **every** environment including dev/staging — enforced entirely server-side, after identity (`requireSuperAdmin()`) and intent (the typed confirmation phrase), before any destructive call. See `docs/production-security-checklist.md` §9 for the operational procedure (the flag should not exist/be true permanently, even in prod, if it's ever needed). |
| T | `properties.internal_address` readable by anon regardless of `show_exact_address_public` | **RESUELTA (Fase 10 Paso 3).** Full call-site audit confirmed zero legitimate app code needs direct anon SQL access to `properties` (the public site already reads it exclusively via the service-role admin client in `public-site.repository.ts`) — so migration `20260903000001_harden_public_property_access.sql` drops `anon_select_published_properties` entirely (least-privilege: revoke direct access rather than build a column-allowlist view the app doesn't otherwise need), plus the 4 neighboring tables with the same "safe rows, unrestricted columns" shape (`property_images`, `unit_images`, `units`, `availability_blocks` — none had a private-column leak today, but removed for consistency and to close the class of risk before a private column is ever added there). A second, distinct leak found during the same audit: `listPublicProperties()` (feeds the public listing's client component) always returned raw `sale_price`/`monthly_rent_price`/`base_price_per_night` regardless of `show_price_public`, serializing the real price into the page's hydration payload even when hidden from display — fixed by redacting those fields at the source, mirroring how `internal_address`/`google_maps_url` were already redacted there. Also hardened `getPublicTenant()` to return `null` for a tenant with `public_site_enabled=false` directly (previously every one of its 6 real call sites correctly checked this flag themselves — confirmed via audit — so this is defense-in-depth with zero behavior change, not a fix for a live bug). Empirically verified end to end (anon blocked on all 5 tables, legitimate public path still works, authenticated tenant access unaffected) via `pnpm validate:security`'s new PropA-PropH test block. |
